# DeepDeck 启动耗时分析（2026-09-13）

主要瓶颈是 Harness 在启动过程中反复生成前端插件的组合脚本与 Source Map。隔离副本中加入缓存后，后台引擎就绪时间的三轮中位数由 **7.302 秒降至 2.675 秒，减少 63.4%（4.627 秒）**。这是引擎就绪计时，不是从点击 Dock 到界面可操作的完整计时。

本次只交付诊断、补丁和验证结果。没有修改 `/Applications/DeepDeck.app`，没有修改上游子模块源码，也没有提交或发布新版本。用户原有工作区改动未动。

## CPU 证据与原因

关闭 Computer Use 的一次 CPU profile 总时长 9.734 秒，主要自耗时如下（采样值，不能当成每次运行的固定时间）：

| 函数 | 自耗时 |
| --- | ---: |
| `buildCombo` | 2.095 秒 |
| `newlineCount` | 1.751 秒 |
| `identitySectionMap` | 1.049 秒 |
| `utf8Write` | 1.168 秒 |

相关逻辑位于 `vendor/deepseek-harness/packages/client/modules/src/index.ts`：

1. 插件陆续加载时，`internal/plugin` 事件将插件标为 dirty，经 microtask 触发 `flush()`。
2. 每次插件表变化，`compose()` 都重新生成全部启动批次，以及每个插件的单独响应。
3. 未变化的插件也重新去除调试尾注、逐字符数换行、生成 identity source map、拼接并序列化映射、编码脚本。
4. 因而虽然插件发现是增量的，输出制品生成仍有大量重复工作。

这条耗时路径来自本地代码计算，CPU profile 不支持把主要原因归到网络更新、遥测请求或 Computer Use 等待上。

## 已验证的优化补丁

补丁：[`harness-client-modules-startup-cache.patch`](./harness-client-modules-startup-cache.patch)。补丁基于上面的 Harness 固定提交，包含源码优化和两项回归测试。

- 按插件记录缓存处理后的源码、换行数和 Source Map section。
- 按插件记录与 revision 缓存单插件脚本及映射响应。
- 按有序插件 ID/revision 列表复用未变化的启动批次。
- 批次缓存只保留当前组合；插件缓存使用 WeakMap，避免每次热更新永久累积旧制品。
- HMR 更新字节或映射时重新生成；插件移除后重新挂载也不会复用旧内容。
- 换行统计改用 `indexOf` 扫描，保持按换行字符计数的语义。

保留原有插件加载顺序、Source Map 内容、组合 URL、上一代响应的兼容窗口和热更新行为。此补丁仍需正式集成后的完整桌面回归与打包验证；它当前是已测量的上游修复候选。

仓库 `AGENTS.md` 明确要求：“不要直接修改 `vendor/deepseek-harness`。该目录视为只读上游源码。”缓存位置是上游 `ClientModuleRegistry` 的私有组装逻辑，普通 Cordis 插件没有可替换的缓存策略接口。因此本次在独立副本验证并导出补丁，正式落地应在可维护的 Harness 上游/分支中修复，再更新 DeepDeck 固定版本；不宜在 Electron 宿主里加入长期的隐式模块 hook。

- 现有测试覆盖 Source Map 消费、映射改动、组合 URL 长度、上一代响应保留、重复包诊断等。

- 未运行整仓 `pnpm check/test/build`：本次没有集成生产代码或提交发行版本；发布前仍需按仓库要求执行完整检查。

## 后续优先级

1. **先集成上述上游缓存修复。** 这是本次有明确对照数据支持的主要收益。
2. **给完整桌面链路加时间点，再优化串行等待。** `bootstrap.ts` 当前等待启动页加载完后才调用 `harness.start()`；窗口创建与引擎启动可以考虑并行，但需处理窗口尚未建立时引擎已就绪、失败或退出的情况，不能简单挪动一行造成丢失状态。
3. **将自动检查更新安排在首屏可交互之后。** 当前引擎启动后 2 秒就触发检查，可能与冷启动争用资源。本次确实观察到旧版下载/解压更新，但它不是已测 CPU 热点，也未量化其启动影响。
4. **Computer Use 等可选工具连接按需或后台初始化。** 当前 MCP discovery 参与 Host 启动就绪条件。改动必须保留首次工具调用等待、错误反馈、关闭设置与进程释放，收益需要单独测量。

不建议以清缓存、删除会话或关闭现有功能作为主要解决办法：它们没有针对本次确认的重复计算，而且清缓存可能增加冷启动成本。
