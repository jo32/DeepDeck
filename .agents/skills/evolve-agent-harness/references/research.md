# Harness 进化与 RSI：研究对照

调研日期：2026-09-24。以下基于作者论文、官方工程文章和项目源码文档。公开实验不等于已在生产中普遍部署；这份材料也不是全行业清单。再次讨论“最新实现”时核查来源版本。

## 如何给一个 loop 命名

RSI（recursive self-improvement，递归自我改进）的使用口径并不统一。下面是本 skill 的工作区分，不是标准等级：

| 实际发生的事情 | 合适的表述 | 还没有证明什么 |
|---|---|---|
| 一次任务中反思、重试、验证答案 | 任务执行循环 | 没有持久改进 Agent |
| 人或外部 coding agent 根据 trace 修改目标 Harness | 评测驱动的 Harness 迭代 | 目标 Agent 没有因此成为自己的改进者 |
| 固定的外层 Agent 自动提补丁、评测、筛选 | 自动 Harness 优化 | 改进机制本身不一定有进步 |
| 更新后的 Agent/改进器继续产生后续版本 | 软件层面的递归自改进循环 | 不保证收益持续，更不证明自动加速 |
| 在同预算、新问题上，更新后的改进器更会产生有效改进 | 改进能力提升的实证 | 仍不能外推无限自改进 |

模型权重保持不变，不妨碍软件层面自改进。真正需要检查的是“谁修改谁、哪些经验被保存、下一轮实际运行哪个版本”，而不是是否使用了多 Agent、反思提示或 RSI 这个名字。

DeepDeck 已记录的流程属于第二行：用户与 Codex 根据 benchmark 和 trace 修改 DeepDeck，再复测。改进后的 DeepDeck 尚未被证明在下一轮承担改进者角色，因此更准确的说法是“为递归自改进提供反馈基础的 Harness 迭代”。具体证据见 [案例](deepdeck-case.md)。

## 公开实现能借鉴什么

| 来源与时间 | 实际机制 | 对本 skill 的启发 |
|---|---|---|
| [LangChain Harness Engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)，2026-02-17 | 固定模型，分析 trace 后修改提示、工具及 middleware | 从可观察的失败机制选择改动，包含验证、预算感知和循环问题；最贴近 DeepDeck 的人工参与流程 |
| [LangChain better-harness](https://github.com/langchain-ai/deepagents/blob/main/examples/better-harness/README.md)，访问于调研日 | 外层 Agent 在临时工作区修改内层 Agent 的有限文件；评测后保留或丢弃，保存历史 | 限定可编辑面，既暴露实现也暴露装配入口；这是可改造的研究原型 |
| [GEPA](https://arxiv.org/abs/2507.19457v2)，2025-07-25，v2 为 2026-02-14 | 从完整执行轨迹反思，生成并评估 prompt 候选，利用不同候选的互补优势 | 给改进者具体工具调用和结果，不只给一个分数；保留有不同长处的候选 |
| [Meta-Harness](https://arxiv.org/abs/2603.28052v1)，2026-03-30 | 外层改进者通过文件系统查阅历代代码、分数和 trace，搜索 Harness 代码 | 可检索的实验档案比越来越长的“经验摘要”更适合作为下一轮证据 |
| [Self-Harness](https://arxiv.org/abs/2606.09498v3)，2026-06-08，v3 为 2026-08-20 | 目标模型从 trace 找自身弱点、提出小修改，再通过回归筛选；不依赖更强的外部改进模型 | 从模型特有问题提出有机制依据的补丁，跨模型收益分别验证 |
| [Sakana DGM](https://sakana.ai/dgm/)，2025-05-30；[论文](https://arxiv.org/abs/2505.22954) | coding agent 修改自己的代码，评测新版本，从不同祖先分支继续探索 | 保存父子关系和失败经验；有研究价值的中间版本不一定是当前最高分版本 |
| [Hyperagents](https://arxiv.org/abs/2603.19461v1)，2026-03-19 | 任务 Agent 和修改它的 meta agent 同处可编辑程序，连产生后续改进的机制也可修改 | 区分“任务做得更好”与“更会改进自己”，后者需要独立的同预算比较 |

GEPA 原论文重点是 prompt；其[当前官方项目](https://github.com/gepa-ai/gepa)还提供更一般的文本/代码优化接口。选择实现时核对当前接口，不把论文实验范围直接扩大成所有 Harness 都已验证。

## 采用这些方法时的判断

**先做能验证的小循环。** 已有少量清晰失败时，DeepDeck 式单候选实验更容易定位收益。候选空间较大、评分可靠且预算明确时，才考虑多候选搜索。无需为了模仿论文引入人口池、分布式调度或多 Agent。

**评测的名字不代表独立性。** better-harness 使用 train 与 holdout 的合计通过数选候选，并提供只在首尾运行的 scorecard。反复用于选择的 holdout 实际承担验证集角色。该项目也明确说明可见/私有数据划分不是强隔离。本 skill 因此另行要求：要声称泛化，使用未参与候选选择的最终测试；这是采用方法时的评测判断，不是声称该项目提供了这项保证。

**任务执行循环和改进循环要分开。** [Anthropic 的长任务 Harness 工程文章](https://www.anthropic.com/engineering/harness-design-long-running-apps)（2026-03-24）展示规划、生成和评价的配合。这样的任务内循环不会自动变成对 Harness 自身的递归修改。工程上还应允许删除不再有用的辅助机制，而不是只增加提示和阶段。

**让改进者接触证据，不让它重新定义胜负。** DGM 官方文章记录了指标被钻空子的现象。实际应用中把评分契约、最终测试与预算执行放在候选修改范围外；这是避免把“改分数”当“改能力”的实验边界。[DGM 原始说明](https://sakana.ai/dgm/)

## 如果要把 DeepDeck 推进到递归实验

先把现有步骤自动化：读开发集 trace → 输出带假设的补丁 → 独立执行评测 → 记录保留/拒绝。冻结外层改进者，先判断自动搜索是否有用。

若再要研究 RSI，让通过验收的新改进者参与下一轮，同时保留旧改进者作为对照。用它们处理新的改进任务，在相同总费用、时间或评测次数下比较结果。将候选生成成本也计入，不能用更多尝试换高分后声称“更会改进”。这一阶段的具体协议见 [实验口径](experiment-protocol.md#验证改进者本身)。
