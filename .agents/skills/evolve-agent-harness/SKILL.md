# Evolve Agent Harness

把一次评测发现变成可复用、可验证的 Harness 改进。优化模型周围的工具接口、提示、上下文、状态、恢复和编排机制；不把换模型、增加推理预算或修改评分标准混称为 Harness 收益。

按用户要求交付调研、实验设计、代码改动或实际复测。仅要求分析时，不启动付费评测或改项目。已有执行、预算及发布授权继续有效；使用这个 skill 本身不会扩展授权。

## 按需读取

- 需要解释 RSI、选择自动优化方法：读 [研究对照](references/research.md)。其中区分工程实践、研究原型和本文的判断。
- 准备评测或解读结果：读 [实验与费用口径](references/experiment-protocol.md)。比较、缓存计费和停止条件以此为准。
- 工具定位、导航失效、schema 稳定性、缓存退步问题：读 [DeepDeck 案例](references/deepdeck-case.md)。这是实例，不是所有框架的必选架构。

## 先确定优化对象

分清四件事：执行任务的 Agent、它实际加载的 Harness、提出修改的改进者、负责判定的评测器。记录谁能改什么。

固定本轮模型与路由、推理/输出预算、任务与环境、评分版本以及基线源码和构建产物。候选可以改变指定的 Harness 文件，也要包含其真实装配入口；只改了未加载的文件不算实验。尊重目标仓库自己的扩展机制。

将既有结果保留为历史基线，必要时另跑同期对照。原始记录不能被新版本覆盖。先检查现有数据是否足以回答问题，避免为“完整流程”重复付费运行。

## 从 trace 找到可修复的机制

选择代表性的失败、成功但昂贵的运行，以及同类正常运行，追到首个偏离预期的步骤。把观察和因果假设分开：低分只能定位现象，不能直接证明模型不会用工具。

| 观察 | 优先核查 | 可能的改动方向 |
|---|---|---|
| 工具名、页面身份或版本填错 | 模型看到的 schema 与宿主要求是否一致 | 由程序保存可确定的身份，提供短引用、封装句柄或业务函数 |
| 跳转后调用旧工具 | 发现、绑定、失效和执行是否使用同一上下文 | 明确绑定生命周期；保留过期拒绝和重新发现能力 |
| 重试增加但结果不明 | 请求未发出，还是发出后回执丢失 | 区分 not_dispatched 与 outcome_unknown；后者先查实际状态 |
| 反复走相同步骤或遗忘信息 | 工具结果、上下文压缩、退出条件 | 小范围改结果结构、记忆或循环检测，并检验误拦截 |
| 轮次少了却更贵 | token 计费语义、稳定前缀、工具列表变化 | 分离稳定声明与动态状态，检查实际未缓存输入 |
| 超时、格式错误、评分异常 | 服务、适配器、运行产物和评测器 | 分开归因；修评分器后重新建立同口径对照 |

每个候选写一个能被推翻的假设：具体 trace 证据 → 机制原因 → 最小改动 → 预期指标变化 → 可能退步的任务。不要同时换接口、模型和任务集后给出单因果结论。

让程序承担它能准确知道的状态，不等于放松校验。工具选择和业务参数仍需模型决定。特别是有副作用的操作，不以盲目重试、忽略版本或把旧请求重绑到新页面换取低错误率。

## 用最小实验检验假设

先用回放、契约检查或已有测试验证绑定、失效、解析等确定性行为，再把模型预算用在行为变化上。成功判定检查实际产物或业务状态，不能只相信模型宣布完成。

发现问题的用例用于开发；保留独立回归覆盖，并在声称泛化时使用未参与选择的最终测试。只有失败子集的复测，只支持该子集的结论。样本少时明确探索性，不将“每题三次”当作统计保证。

同一候选分别看各模型、各任务。合计成功率先满足预设质量底线，再比较耗时、轮次、工具错误、含缓存费用。报告权衡和不确定性，不把一个加权总分替代用户目标。对照不可比时输出“证据不足”，不要强选赢家。

## 留下下一轮能用的证据

沿用项目已有实验目录。每个候选至少留下父版本、假设、差异、实际运行配置、全部尝试、指标、退步与保留/拒绝/待验证决定；原始日志与可分享的脱敏摘要分开。失败候选也有价值，不只保留赢家的一行分数。

默认完成一个与当前问题相称的迭代。多轮搜索使用明确的时间、费用或评测次数上限，并计入改进者、失败尝试和验证的开销；达到首个上限即结束。沿用用户给定预算；若只获准研究，则给出后续实验估算。已授权的小规模复测可选择并说明最小有用规模，不要求无意义的再次确认。

自动搜索可以保留不同优势的候选以备探索，但“值得保留作研究”不等于“可发布”。单独有效的补丁合并后，需要验证组合效果；提升依据和回退到哪个已知版本应可复查。

## 何时讨论递归自改进

固定外部改进者反复优化目标 Harness，先称为自动 Harness 优化。若新版本又参与生成下一代修改，则出现软件层面的递归反馈；不要求训练模型权重。

若用户要验证“连改进能力也提升了”，对旧、新改进者在新问题、相同预算下比较有效改进数量、最终独立测试表现和搜索总成本。任务分数上升本身不证明改进能力变强或加速。

仅在任务确实包含该目标时，才允许修改改进者的提示、搜索、记忆等机制。候选不能修改本轮评分契约、最终测试答案、预算控制和结果记录来提高分数；评测器确有错误时单独修复并重建对照。

## 交付

用具体证据解释“哪里出错、改了什么、为什么可能有效、实测怎样”。链接代码差异和逐次数据，列明成功率、耗时、含缓存费用、退步用例、比较限制，以及保留/拒绝/继续验证的决定。按已有授权完成提交或发布；没有这类任务时，交付可审阅结果即可。
